# Inspection latency

The 2026-09-27 Ask70 run `r7_1d3a575_20260927T121849Z` reached local preparation and then rejected at the final gate with `entry_price_moved`. No POST was sent. The execution journal’s `OrderPrepared` event records `prepare_queue_wait_ms=17672`, `refresh_wait_ms=0`, `tick_resolve_ms=0`, and `create_market_order_ms=0`. The following `OrderPreDispatchFailed` event leaves those timing fields null, and both the reducer and the timeline copy nulls over the earlier measurements.

`refresh_wait_ms=0` shows the preparation path did not see a normal account refresh. The wait is the shared SDK slot, which startup inspection holds for the whole read, including activity pagination and Polygon payout calls.

## Decisions

- Background inspection uses a second `AsyncSecureClient` created with the same existing API credentials. Each SDK client owns its own context, caches, and transports. The inspection client is never the execution client and never takes the execution SDK slot. Account-state refresh still uses the execution client and its single-flight slot.
- The gateway creates and closes both clients, including when inspection-client creation fails and on shutdown. In-flight POST draining stays in front of client close.
- An inspection captures the journal tail and the set of unresolved attempt ids before any network read. A changed tail or a changed unresolved set discards the result. A stable but non-empty unresolved set is published as classification only: auto-clearance is withheld because the submission response has not arrived. Completed mutation counts are not the consistency check. Discarded and withheld results do not expire a still-valid assessment.
- Readiness stays valid for `monitor_interval_s + inspection_budget_s`. The next inspection starts one inspection budget before that deadline, so a normal recheck finishes inside the current window. An incomplete read or a real account block still fails closed.
- Recurring activity uses the SDK `start` filter, timestamp sort, and page size 500. The first read and every 12th accepted read are complete. The checkpoint stores schema, wallet, chain, environment, query scope, coverage timestamp, overlap (120s), and the activity ids at that timestamp. It is one journal meta document with the accumulated activity rows. It is written only after the execution epoch is still accepted, the account evidence is complete and internally consistent, and the evidence events have been appended. Evidence is appended before the checkpoint. A later execution change during that publication leaves the checkpoint unchanged. Dedup is `activity_id`, not transaction hash. A failed, truncated, incomplete, or inconsistent read does not move it. The assessor receives the accumulated rows, not the delta alone.
- A Polygon `latest` payout read is not reusable clearance evidence. The current adapter does not supply a finalized block identity, so the settlement cache does not satisfy clearance and every inspection reads the payout again on the inspection client. Unresolved reads, failures, mapping mismatches, and neg-risk stay unresolved. Holdings and open orders are always read fresh.
- Timing and cache-miss fields merge by presence. `None` means the event did not measure the field. `0` is a real measurement and is kept.
