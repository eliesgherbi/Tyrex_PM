## Direction agreed with the user

Keep the brand, appearance, navigation and paired Up / Down Explorer charts. Keep the current Data Library's recording selection, filters, coverage, saved sets and preparation plan. Retain the existing workflow operations and execution engine as the backend authority.

Replace preset A/B configuration cards with an explicit draft:

1. Choose a strategy supported by the workflow adapter.
2. Start from strategy schema defaults, a source YAML, a saved configuration or, when supported, a candidate.
3. Edit six visible essentials; expand a role-based group, search, or show all parameters for complete control.
4. Name and validate the configuration. Saving it for reuse is optional and distinct from including it in this batch.
5. Add another configuration only when requested. Existing validated configurations remain visible and editable. An open edit must be validated or discarded before batch preview.
6. Preview the exact experiments, complete effective parameters, execution assumptions, windows and workload. Then run, stop or resume.

The draft survives navigation within the review browser session. Changes remain browser-only and do not modify project configuration files.

## Changes to the earlier mockup

- Replay is a mode, not an automatic comparison or tuning exercise. It uses the whole saved set, with no objective, hidden partition or ranking.
- The window set displays its policy and recordings. It is not labelled a development population. Only Tune introduces development / holdout membership.
- Replace invented execution scenario labels with the project's `friction` and `favorable` templates. Display and edit their assumptions separately from strategy parameters.
- Rename Plan to **Preview**. Back to editing retains the configuration draft; replay starts only from a reviewed snapshot.
- Results begin with compact strategy groups. Opening a strategy reveals its searchable, paged run history; configuration tabs identify the selected dashboard and ledger. A selected-run switcher keeps the ownership explicit. There is no combined multi-configuration P&L total.
- Qualified simulated P&L excludes unqualified rows. Those rows remain visible and inspectable, including partial fills and unknown outcomes. Qualification is scoped to the research policy; it is not paper qualification.
- Explorer retains the paired model/book charts and aligns a selected time with decision, execution, inputs and identity. Candidate save comes from that selected result/configuration.
- Candidate has a rationale, exact resolved values and result identity, Replay origin, and **no holdout evaluation**. Freeze and paper export review are separate actions.
- Tune is explicitly **Phase 3**. The design preview introduces a grid, objective, chronological tail per recording, top-k, development ranking, holdout generalisation and stability. It cannot launch a tuning job.
- Compare is a view across saved results. Different populations or assumptions allow descriptive comparison but do not justify a paired improvement claim.

## Parameter ownership

The design snapshot was generated by reading the actual settlement configuration schema and source YAML on 22 October. It contains **81 strategy fields** in 11 sections, plus **27 fields** in each execution scenario template.

Six essential controls are visible first: entry edge, minimum and maximum remaining time, acquisition spending cap, maximum entry price and lifecycle policy. The other controls are grouped as:

- Entry and position size.
- Model and volatility.
- Exit, retry and re-entry.
- Settlement and research policy.
- Strategy fee estimates.
- Model / market disagreement.
- Execution assumptions, including their own fee convention.

The two input-admission fields derived from `exploratory95_v1` are visible, marked as policy-owned, and included in the resolved configuration **before** validation. They are not silently merged after validation. Changing the admission rule belongs in Data's policy selection and creates a different saved set. Scenario source identity fields are metadata; the remaining execution assumptions are editable.

Only `settlement_value` is enabled because the current workflow experiment adapter refuses other strategy kinds. Ask70 and z_gap explain that their workflow adapter is unavailable. An implementation must obtain this information from backend capabilities rather than hard-coding frontend support.

Loading the paper YAML here imports its **strategy parameters** as a base, not its venue/account/operational host settings. Paper operational fields belong to the later export report.

## Experiment and run grouping

The document defines one strategy and execution context per experiment. The user's preferred “add another replay” flow is therefore a **batch of explicit configuration entries**:

- Same strategy and identical resolved execution assumptions can share an experiment containing several configurations.
- A different strategy or execution context becomes another experiment and run within the same batch.
- Each history row identifies its run and experiment; each configuration's dashboard owns only that result. The UI does not add results across configurations as if they were separate market observations.

Grouping, schema validation, policy compatibility, exact workload and replay-unit construction must be authoritative backend operations in the integrated implementation. Local design checks are not proof that every schema constraint has been validated.

## What is implemented today versus proposed

Inspected `frontend/src/Operations.tsx` still binds a selected set with `parameters: {}`, starts/polls jobs and opens result rows / trace availability. Its candidate form is not yet the selected-result snapshot shown in this proposal. The current workflow bind still imports the development-partition check and applies exploratory quality values at bind time. Removing those behaviours is Phase 1/2 backend work; the mockup does not remove them.

The revised UI is a separate design app. All result cards, charts, qualification examples and replay progress are synthetic fixtures. Parameter edits do **not** calculate new strategy performance. Saved configurations, drafts and candidates use this review browser's session storage. A displayed source policy is not a warehouse assessment. No collector, real replay, paper session or order was launched, and no project YAML was written.

## Export check discovered during inspection

The requirement says research-only tolerances must not leak into a runnable export. In the inspected `workflows/profiles.py`, `profile_generate` copies `candidate["parameters"]`, validates the strategy/run configuration and rejects `operational.research_defaults`. That flag check alone does **not** establish a comprehensive check of every research-tolerance field in candidate parameters. Keep the exporter requirement, but add a concrete acceptance check for incompatible quality/payout/input tolerances. Do not present that behaviour as already proven. The mockup's export drawer therefore shows preserved / added / unresolved fields and requires backend validation; it generates no YAML.

## Review tour

1. Replay: load defaults or the YAML, edit an essential, search for `backoff`, inspect a group, validate and name it. Save a reusable configuration if useful.
2. Add another configuration, optionally reuse the saved one, modify it and validate. Preview should list the correct units and experiment grouping. Inspect both strategy and execution values.
3. Start the demo, stop, then resume the same job. Open its results.
4. Select a run and a configuration. Verify that the owner labels, metrics, chart and window ledger change together. Inspect an unqualified partial fill or blocked window.
5. Save from the chosen result, give a rationale, freeze once and review export requirements.
6. Open “What changes?” to review the keep / move / later boundaries. Tune is a separate future-design preview.

## Navigation review follow-up · 22 October

This supersedes the earlier large run-card layout. The approved parameter editor, result dashboard and paired Up/Down Explorer charts are retained.

- Replay is titled **Replay**. Its first card shows the selected window-set name, exact identity and prominent window count. **Choose / change window set** opens the selector. Data offers **Use in experiment** on each saved set. Both paths start a fresh replay draft for that set.
- Two design fixtures (eight windows and its first four windows) make the handoff testable. Workload, summaries, chart categories, ledger and Explorer navigation follow that exact set; a four-window selection cannot expose the other four windows. These fixtures do not query the integrated warehouse.
- Validating a configuration presents two immediate choices: **Preview replay** or **Add another configuration** to this replay. An unfinished editor must be validated or discarded before preview.
- Completed playback offers **Start a new replay**. A **New replay** action also appears on result and other research pages. This clears only the current set's draft, resets its configuration list and reviewed preview, and retains completed history, reusable configurations and candidates. Returning to a completed batch keeps that batch inspectable until the user chooses a new replay.
- Results group by strategy, defaulting to the latest saved run on first opening. A strategy card opens that strategy's latest run and its compact history. History supports text search (run, configuration or set), status, newest/oldest order and five rows per page. Filtering history does not replace the dashboard currently being inspected. Opening a history row selects its run; configuration tabs keep all metrics and charts owned by one result.
- Saved design run history now survives a page refresh within the same browser session. A demo interrupted by refresh is marked stopped; there is no automatic job launch.
- Tune remains a Phase 3 sketch. **Show Tune preview** scrolls to an explicit design-only preview; execution remains disabled. It does not start a real or simulated tuning job.

The integrated application on port 4173, the other proposal on port 4175, project configurations, backend and warehouse remain unchanged by this revision.
